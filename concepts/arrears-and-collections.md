# Arrears and Collections

This document outlines the payment collection lifecycle, retry mechanisms, arrears workflows, and missed payment notification pathways managed across `billing-service` and its downstream integrations.

---

## 1. Collection Lifecycle

Payment schedules for policies are generated by [[entities/plan-service|plans.Service]] and stored in [[entities/plan-model|payment_plans and instalments]]. 

1. **Instalment Due Event:**
   When an instalment collection date arrives, `billing-service` emits the Pub/Sub event `billing.instalment.due` (topic `billing.instalment.due`).
   - Defined by `events.InstalmentDue` in `internal/events/publisher.go`:
     ```go
     type InstalmentDue struct {
         PlanID      string `json:"plan_id"`
         PolicyID    string `json:"policy_id"`
         CustomerID  string `json:"customer_id"`
         Instalment  int    `json:"instalment"`
         AmountPence int64  `json:"amount_pence"`
         FeePence    int64  `json:"fee_pence"`
         DueDate     string `json:"due_date"`
     }
     ```
2. **Payment Collection Request:**
   Collections are initiated against `payments-gateway` via `POST /v1/collections` (using an `idempotency_id` to prevent duplicate billing; see [[entities/downstream-clients|Downstream Clients]]).
3. **Successful Collection:**
   When a collection completes, `payments-gateway` emits `payments.collection.succeeded`. `billing-service` consumes this message via subscription `billing-collection-succeeded` and calls `store.MarkCollected` to update the instalment status in the database.

---

## 2. Failed Collections & Retry Policy

When an initial collection attempt fails through Direct Debit or card processing:

1. **First Failure:** `payments-gateway` automatically schedules a single retry after **3 working days**.
2. **Second Failure (Final Failure):** If the collection fails on the second attempt, `billing-service` publishes the `billing.payment.missed` event (topic `billing.payment.missed`).

### `billing.payment.missed` Event Payload

Defined by `events.PaymentMissed` in `internal/events/publisher.go`:

```go
type PaymentMissed struct {
    PlanID     string `json:"plan_id"`
    PolicyID   string `json:"policy_id"`
    Instalment int    `json:"instalment"`
    Attempts   int    `json:"attempts"`
}
```

---

## 3. Arrears and Policy Cancellation Lifecycle

When `billing.payment.missed` is published after two failed attempts, external systems trigger downstream arrears and debt management processes:

```
[ Collection Fails (1st Attempt) ]
               │
               ▼ (Wait 3 working days)
[ Collection Fails (2nd Attempt) ]
               │
               ▼
[ Publishes: billing.payment.missed ]
        │                       │
        ▼                       ▼
[ notifications-hub ]     [ policy-admin ]
  Sends SMS Alert          Initiates 14-day cancellation letter workflow
```

- **SMS Notification:** `notifications-hub` consumes `billing.payment.missed` and immediately sends an SMS text message to the customer notifying them of the missed payment.
- **14-Day Cancellation Notice:** `policy-admin` consumes `billing.payment.missed` and initiates the statutory 14-day cancellation letter workflow.

## 4. Known Limitations and Issues

### Outdated Arrears Letter Address (TWPOL-4 / Bug)
- **Root Cause:** As noted in `internal/events/subscriptions.go`, `billing-service` **does not subscribe** to `customer.profile.updated`. Billing retrieves customer address details only once during plan generation via `GET /v1/customers/{id}` from `customer-identity`.
- **Impact:** Arrears and fee warning letters generated from `billing-service`'s snapshot use the initial address. If a customer updates their address after plan creation, letters are sent to the old address (e.g., 140 letters were returned in August 2026).
